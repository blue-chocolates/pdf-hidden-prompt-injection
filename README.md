# PDF Hidden Prompt Injection

PDF 文档读取差异与间接提示注入的安全研究原型。核心问题是：**页面上看不见的内容，是否仍会被文档处理系统读取？如果被读取，系统会把它当作资料，还是当作指令？**

`pdf-hidden-prompt-injection.py` 是基于 Python 和 PyMuPDF 的本地实验脚本。它读取 PDF，在页面加入测试文本并另存为新文件；不调用模型，也不上传文档。它不是检测器、脱敏工具或纯压缩工具。仅需压缩时，请使用独立的 `compress_pdf.py`。

## 常见的 PDF 读取方式

PDF 查看器把页面渲染成可见画面。程序如果要读取文字、表格或图表，则可能走以下路径：

| 方式 | 怎么读 | 常见用途 |
| --- | --- | --- |
| **直接提取文本层** | 用 `pdftotext`、PyMuPDF 或 `pypdf` 解析 PDF 内部的文本对象，不用 OCR。 | 适合 Word 等软件直接导出的电子文档。双栏、表格或字体映射异常时，提取顺序和字符可能与页面显示不同。 |
| **渲染后做 OCR** | 先把页面渲染成图片，再用 Tesseract 等工具识别像素中的文字。 | 适合扫描件、截图或没有可用文本层的页面。清晰度、语言和版式都会影响识别结果。 |
| **多模态视觉读取** | 将页面图像交给能处理图像的模型，由模型理解页面内容。 | 适合图表、示意图和需要结合版面理解的内容。与单纯 OCR 不同，模型可以结合视觉上下文回答问题。 |
| **版面分析与混合提取** | 结合文本提取或 OCR 与版面分析，识别段落、表格和行列关系。 | 适合复杂版式的结构化提取，例如 [Azure Document Intelligence 的版面分析](https://learn.microsoft.com/en-us/azure/ai-services/document-intelligence/prebuilt/layout)。 |

### AI 应用如何读取上传的 PDF？

- **文本链路**：应用先提取正文，必要时对扫描页做 OCR，再把整段文字或检索到的片段交给语言模型。模型通常只看到文字，不一定看到原始排版。
- **视觉链路**：应用把页面渲染成图像，再交给多模态模型。模型主要依据画面，不能仅凭图像看到未被渲染出来的文本对象。
- **混合链路**：应用同时提供提取文本和页面图像，或按页选择读取方式。例如，正文用文本层，扫描页走 OCR，图表再交给视觉模型。

所以，**支持上传 PDF 不等于使用 OCR，也不等于模型看过每一页**。评估某个 AI 应用时，要区分页面显示、提取结果和最终送入模型的内容。

## 实验观察

| 观察 | 如何判断 |
| --- | --- |
| **页面预览和提取文本可能不同。** | 对照同一页的渲染结果和原生提取结果，记录只在其中一边出现的内容。一种工具的结果不能代表整个处理链路。 |
| **Word 导出后，缺字有时看起来像多余空格。** | 在部分样本中，极小字号的文本导出后出现缺字和文本片段断裂。排查时先确认 UTF-8 编码，再用 `Page.get_text("dict")` 检查实际写入的文本片段（span），比对字符、字号和位置；不要仅凭复制结果认定是 Word 插入了空格。首行排版差异的根因尚未确认。 |
| **提取到了，不代表模型执行了。** | GPT-6.2-Sol摘要测试识别出了页面上不易察觉的测试指令，却没有按它行动。评估时应分别记录页面是否可见、解析器是否提取到、下游是否将内容当成指令。单个样本不能代表其他工具、模型或版本。 |

不可见的文字本身并不是攻击证据：扫描件常有正常的 OCR 文本层，供搜索和复制。风险在于文档内容跨越了信任边界。对接 AI 时，应将来自 PDF 的内容标记为外部数据，不让文档中的指令直接触发工具调用或业务操作。参见 [OWASP：间接提示注入](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)。

## 实验脚本：`pdf-hidden-prompt-injection.py`

### 脚本做了什么？

1. 用 PyMuPDF 读取本地 PDF，只在第一页添加测试文本。
2. 为可处理的嵌入字体生成子集，只保留实际用到的字形；随后压缩 PDF 内部对象和数据流。这一步用来控制文件体积，不负责修改图片质量或清理敏感内容。
3. 将结果另存到输入文件所在目录，文件名形如 `sample-inject.pdf`。输入原件不被覆盖；如果已有同名输出，应先保留旧副本，以免重写。

### 如何核对实验结果？

1. 在 PDF 查看器里对比原件和实验副本界面，记录页面上能看到什么。
2. 按下方「检查 PDF 的文本层」的方法分别提取两份文件的文字，核对哪些内容只出现在提取结果里。若流程含 OCR，可用页面渲染图另做一次对照。
3. 分开记录**页面是否可见**和**解析器是否能读到**。这个脚本不调用模型，因此不能仅凭输出 PDF 或提取结果得出模型会执行其中内容的结论。

## 用法：检查 PDF 的文本层

用不含个人信息的样本。Windows 用户可从 [Poppler for Windows](https://github.com/oschwartz10612/poppler-windows) 的 Releases 下载预编译包。解压后，使用 `pdftotext.exe` 提取文本，与 PDF 查看器中同一页的显示结果对照：

```cmd
pdftotext "sample.pdf" -
```

重点检查预览中找不到的段落、缺失字符和异常断行。若需定位字符在页内的位置，可用 [PyMuPDF 的结构化文本提取](https://pymupdf.readthedocs.io/en/latest/textpage.html#TextPage.extractDICT) 辅助排查。一次提取没有异常，不等于文件没有可疑内容；结论只适用于实际检查过的提取路径。

## 附带发现：Microsoft Word 导出的 PDF 还能无损二次压缩

部分 Word 导出的 PDF 即使已通过 Office 优化，仍有体积可减。这个方法整理的是 **PDF 内部对象和数据流**，不删减页面内容、不把页面栅格化，也不对图片降采样或做有损重编码。未压缩的数据流可以进行无损压缩，图片像素分辨率不变。

| PyMuPDF 保存参数 | 作用 |
| --- | --- |
| `garbage=3` | 清理未引用对象、整理交叉引用表并合并重复对象。 |
| `deflate=True` | 无损压缩尚未压缩的数据流。 |
| `use_objstms=1` | 将符合条件的对象打包进对象流，减少结构开销。 |

纯压缩无需重新嵌入字体或重新生成字体子集。压缩比例取决于原文件；已经充分优化的 PDF 可能几乎不变。这里的「无损」不等于前后文件字节完全相同；重新保存可能使数字签名失效。参见 [PyMuPDF 保存参数说明](https://pymupdf.readthedocs.io/en/latest/document.html#Document.save)。

### 用法：仅压缩，不写入测试文本

在独立脚本 `compress_pdf.py` 所在目录运行：

```powershell
python -m pip install -U PyMuPDF
python compress_pdf.py "word-export.pdf"
```

输出 `word-export-compressed.pdf`，与输入文件放在同一目录。脚本不覆盖原件或已有输出，也不需要额外字体。可用打印出的字节数记录压缩效果，并对照前后的页数、页面显示和提取文本。
